
## Part 6: Product Recommendation

I’d make the agent check whether a request went through before telling a patient it’s done. In one test, a caller asked to move an appointment to Thursday at 2 p.m. The scheduling system moved it, but the agent received only a timeout. It confirmed the new time anyway. Had the change failed, the caller could have shown up for an appointment they didn’t have. The revised agent looked up the original request and confirmed the slot in one extra step, without making the caller repeat anything. I’d test timeouts both before and after a booking changes. In either case, the patient should hear an accurate answer and the system should record at most one booking. 

Across 26 synthetic scenarios, the original agent claimed success without enough evidence in three. The revision corrected all three. In two, the appointment change or refill submission had failed. The revised agent explained that and got the caller’s agreement to a callback, bringing staff requests from four to six. My second priority would be making those callbacks useful. In a separate refill test, the note “Please call the patient” passed the handoff check despite omitting the medication and pharmacy. I’d carry the caller’s confirmed details, the failed action, the responsible team and the deadline into the task. Then I’d ask refill staff to handle sample tasks from the notes alone and flag anything they’d have to ask the patient again.

I’d keep identity verification as a release condition. In a separate test, the tool blocked an early attempt to read an appointment. The agent later verified the caller and booked successfully, so the final booking alone would hide the unsafe attempt. If identity remains unresolved, the agent should stop before opening the record and explain the clinic’s next step. Urgent calls still need the clinic’s approved route for callers who cannot verify. 

These cases were chosen to expose failures. To learn how often patients encounter them, I’d first run the revised logic alongside the live system without changing what patients hear or writing to their records. For a sample of calls at each clinic, I’d match spoken confirmations to booking and refill records and count how many were supported when the agent spoke. In a limited rollout, I’d also track duplicate requests, time callers spend waiting, callbacks completed by the promised deadline and patients who call back about the same issue. Those measures tell the team whether more reliable answers are worth the extra lookup and staff time.

## Part 7: Product Design

At thousands of calls a day, I’d move scoring into a background queue so it never holds up a conversation. For each call, I’d link the time-stamped conversation, identity checks, tool responses, clinic records and callback updates using call and request IDs. Workers could retry an interrupted job without counting the call twice. If a booking confirmation arrives late, the workbench should retain the original result and show the updated outcome. An engineer could then see both when the booking happened and what the agent knew at the time.

Each result should record the agent build and its instructions, the tool version, the clinic policy in force during the call and the version of each scoring rule. Replays should also record the scenario version and seed. That lets a reviewer distinguish a change in agent behavior from a clinic changing its callback deadline. I’d encrypt call records, restrict access by clinic and role, hide identifying details by default, log who opens a transcript and delete records on the clinic’s retention schedule.

For cost and speed, I’d score new calls first and schedule historical reruns when capacity is available. I’d monitor cost per thousand calls, the age of the oldest waiting call and the share of calls missing a clinic response. A spike in missing responses at one clinic should alert the integration owner. Reviewers should see those outcomes as unknown, with a link to the last event received.

I’d send suspected safety failures to a reviewer and also sample ordinary passes and unknowns from each clinic and workflow. Reviewers would label calls before seeing the automated score. Tracking missed problems and false alarms over time, and periodically rescoring a fixed set of independently labeled calls, would help distinguish a scoring rule that has become unreliable from a change in the calls themselves.

Before a release, I’d compare both agent versions on the same cases under the same rules. A new unsupported confirmation or attempt to open a record before verification would block rollout. After those checks pass, I’d start with one clinic and expand only if confirmations hold up and callbacks stay on time. Each confirmed failure would go to the team that owns the workflow, with a redacted trace and a test that reproduces it. The team would close the issue after the fix passes replay and the same problem declines in reviewed calls.
